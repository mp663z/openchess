# T0260 Store/idempotency/implement

## Normative requirements

1. `store.idempotency` implements `IdempotencyError`, `IdempotencyEngine(request_fingerprinter)` with `apply(log, ledger, request)`, `request_fingerprint` (the canonical derivation and honest fingerprinter), `derive_receipt_id` and `FAILURE_MAPPING` for data/contracts/idempotency.yaml. Production must not import or execute `tests.*`.
2. The request is an exact dict with exact-str keys `{idempotency_key, op, payload}`, a key in the pinned grammar, and an op and payload the linked WAL accepts. Validation goes through the WAL's public `append` on an empty scratch log (the trusted canonicalizer cannot fail, so every rejection is the request's). Otherwise `malformed_idempotency_request`.
3. The source log validates and replays through the linked production WAL, and any rejection is `corrupt_source`. The ledger is validated in full (exact receipt shape, grammars, receipt-id re-derivation, unique keys, strictly increasing sequences within the log, binding to the exact live entry id and fingerprint) before any oracle call, or it fails `corrupt_ledger`. Only names in `store.wal.__all__` are used.
4. The fingerprinter is untrusted: exactly one call on a detached copy of the frozen request. Any BaseException, non-exact-str, wrong-grammar or non-UTF-8 output, or a token not byte-exact to `request_fingerprint`, fails closed as `divergent_fingerprint`.
5. Deduplication is key then byte-exact fingerprint. A seen key with the same fingerprint returns the stored receipt (`replayed`, no append). A seen key with a different fingerprint fails `key_conflict`. An unseen key stages the WAL append on a detached log copy and commits entry and receipt together last (`applied`). Log, ledger and request are restored bit- and reference-identical on every exit.
6. The T0259 red battery turns green by replacing only its two binding lines. Every scenario, probe and mutant stays unchanged.
