# T0261 Store/idempotency/unit/property

## Normative requirements

1. The battery exercises only the shipped production idempotency (`store.idempotency`, T0260). Logs and entries are built by the shipped `store.wal` from records made by the shipped `graph.node` runtime. It imports nothing from `tests.*`. Properties are deterministic and seeded.
2. On every seeded request sequence, `apply` matches an independent key-then-fingerprint model:
   - a new key is `applied`: the log grows by exactly the entry the WAL appends for the request, and the receipt (in contract field order) carries the key, the independent fingerprint, the new entry id, the new sequence and the independently derived receipt id; the ledger gains an equal receipt;
   - a known key with the same fingerprint is `replayed`: the stored receipt is returned, and log and ledger are untouched;
   - a known key with a different fingerprint is `key_conflict`, and log and ledger are untouched by value and identity.
   The fingerprinter is called exactly once per apply, with the request op and a plain copy of the payload. Existing log entries and receipts keep their identity.
3. Replay is stable: re-applying any ledgered request replays an equal receipt that is not the stored object. A conflicting request never overwrites. The same request under a new key applies again at the next sequence.
4. `request_fingerprint` and `derive_receipt_id` equal independent sha256 derivations, including the length framing and domain prefix. Distinct op/record requests give distinct fingerprints. The fingerprint derivation never touches its input.
5. The fingerprinter argument is detached: mutating it at every level never reaches the log, ledger, request or receipt.
6. At the fingerprinter boundary, a forged typed error fails as `divergent_fingerprint` with the mapped code and never surfaces as the forged class: an `IdempotencyError` for every failure class other than `divergent_fingerprint`, and a forged `WalError` of every class. So does any other BaseException, and None, bytes, str subclass, trailing newline, upper case, surrogate or grammar-valid but wrong output, on a new key and on a known key. Log, ledger and request stay untouched.
7. A fingerprinter closing over the live log, ledger and request that mutates them at every level (including deleting and re-adding the request key with another grammar-valid key) is undone on the applied, replayed and failing paths; on success only the committed entry and receipt are appended, and the receipt and ledger carry the original key.
8. Malformed requests fail as `malformed_idempotency_request` before source, ledger and fingerprinter, even over a corrupt log (a chain tamper, or a str-subclass or hash-colliding key at entry, payload or record level) or a corrupt ledger: renamed, missing, extra, str-subclass and hash-colliding keys at request, payload and record level; dict subclass, list or None requests, payloads and records; bad key grammar (empty, 129 chars, leading dash, space, newline), str-subclass or int keys; unknown, str-subclass or None ops; wrong digest, mismatched or str-subclass identity. Keys at the grammar edges are accepted.
9. Any single-entry source tamper fails as `corrupt_source` before the ledger and the fingerprinter, typed and never raw, with a valid or corrupt ledger. A non-list log, including a list subclass, is `corrupt_source`.
10. Any ledger tamper fails as `corrupt_ledger` before the fingerprinter, with log, ledger and request untouched: non-list or list-subclass ledgers; dict-subclass or non-dict receipts; renamed, missing, extra, str-subclass and colliding keys; bad or str-subclass keys and identifiers; bool, int-subclass, float, zero, negative, over-log, duplicate (including a duplicate sequence that is otherwise fully bound) or descending sequences; duplicate keys; a flipped receipt id; a wrong entry or fingerprint. A receipt at the log's last sequence is accepted and one past it rejected; an empty ledger is valid.

## Mutation check

Each of these one-line production mutants of `store/idempotency.py` turns the battery red on its own:
- Fingerprinter boundary (the one `except BaseException` in the module): `except IdempotencyError: raise` ahead of the catch-all; `except _wal.WalError: _fail("corrupt_source")` ahead of it; `except Exception` instead of `BaseException`; and one forged-class passthrough per class, each letting exactly that class escape: `IdempotencyError` `corrupt_ledger`, `corrupt_source`, `key_conflict`, `malformed_idempotency_request`, and `WalError` `corrupt_chain`, `divergent_canonicalization`, `malformed_wal_entry`, `sequence_conflict`, `unknown_operation`. Also isinstance output, the type check removed, the binding to the local derivation removed, and the live frozen payload passed without a copy.
- Derivations: fingerprint length framing dropped, op or FEN dropped, domain prefix dropped; receipt id arguments swapped or the sequence dropped.
- Request: isinstance request, key-type check removed, key set replaced by a length or superset check, key check removed, `_valid_key` loosened to isinstance or prefix match, WAL validation removed, WAL rejection narrowed to one class.
- Source: WAL replay removed or narrowed to one class; ledger validated before source; request validated after source; the log key guard moved ahead of request validation.
- Ledger: validation removed; isinstance ledger or receipt; key-type check removed; key set replaced by a length or superset check; key check removed; identifier isinstance; isinstance sequence; `seq < last` instead of `<=`; `>= len(log)`; no upper bound; no ordering; duplicate-key check removed; receipt-id check removed; entry or fingerprint binding removed; entry lookup off by one.
- Dedup and commit: key-only dedup; first receipt only; dedup by fingerprint; replay returning the live stored receipt; no log restore; no receipt value restore; receipt `update` without `clear`; no ledger container restore; no request, payload or record restore; restore only on the failing path; entry or receipt not committed; staging on the live log; receipt sequence off by one; the receipt key read from the live request instead of the frozen one (a fingerprinter closing over the live request rekeys it mid-call).

These mutants are equivalent and stay green:
- Fingerprint output: `match` instead of `fullmatch`, the grammar check removed, or the UTF-8 check removed. The output must still equal the local derivation, which is always a grammar-valid ASCII string, so the binding rejects every such output with the same class.
- Request guards: isinstance op, the payload key guard removed, or the record key guard returning True. The linked WAL's append validation (exact str op, exact str keys checked before any set comparison) rejects the same inputs, mapped to the same `malformed_idempotency_request`.
- Source guards: the log key guard removed, or checked only at entry level. `wal.replay` has the same exact-str-key guards and rejects the same logs as `corrupt_source`.
- Ledger identifiers: `match` instead of `fullmatch`, or the grammar check removed. The fingerprint and entry id must equal the bound log entry's and the receipt id must equal its derivation, all of which are exact grammar-valid strings.
- `ledger.append(receipt)` without a copy, or returning `receipt` without a copy (each alone). The other copy still keeps the ledger receipt and the returned receipt distinct.

The mutant list is prose only. There is no GENERATED-CHECKED block; each mutant was applied one at a time, with bytecode caching off, and run against this battery.
