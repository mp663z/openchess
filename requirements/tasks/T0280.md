# T0280 Store/crash resume/fuzz/fault

## Normative requirements

1. The battery is deterministic and seeded. It fuzzes the shipped production crash resume (`store.crash_resume`, T0278). Every input log is built from an independent model of data/contracts/wal.yaml and data/contracts/crash_resume.yaml, then torn at a known position. The model restates the entry-id derivation, the put/delete fold, the quarantine token and the resume-id derivation in the test and never takes them from production. `graph.diff.state_id` supplies state ids, and the contract reference engine (`tests.test_t0275_crash_resume_contract`) is the differential oracle for every case.
2. The eight generators produce 351 cases:
   - `happy` (64): random logs with a tail of 0-3 entries and any checkpoint up to the prefix.
   - `tear` (39): all 13 WAL-invalid but admissible tear shapes, followed by honest-looking entries.
   - `request` (34): 17 malformed requests, over a clean log and over an inadmissible log. They include renamed, missing, extra and non-ASCII keys, str-subclass and colliding keys, a dict subclass, list or None request, and a bool, int-subclass, float, str, None or list checkpoint, with negative checkpoints that carry an extra key or are an int subclass.
   - `checkpoint` (24): a negative checkpoint over an inadmissible log, a checkpoint past the log, and a tear at or before the checkpoint.
   - `container` (6): non-list and list-subclass logs.
   - `admission` (81): 6 admissible and 21 inadmissible values, placed as the tear, after the tear, or inside an acknowledged entry. The depth bound is placed exactly at MAX_DEPTH and MAX_DEPTH + 1 for each position.
   - `sink` (64): a forged `ResumeError` of every class, a forged `WalError` of every class, six BaseException kinds and 15 bad outputs, plus a scribbling sink. The bad outputs are None, bytes, int, list, str subclass, upper hex, a trailing newline, a leading space, another prefix, a flipped digit, and the token of the empty, a shorter, a longer, a reversed and an ASCII-escaped tail.
   - `live` (39): a sink edits the caller's live log and request (keys added at every level, values changed, fields dropped, container append, insert, delete, reverse and clear, request key added, checkpoint changed, request cleared), then answers honestly, raises or returns a flipped token.
3. Every case holds against production. There is no raw escape: failures are only a typed `ResumeError` with its mapped code. The outcome is the independently known one and the same as the contract reference. At the sink boundary the error is FRESH, never the forged object. The sink is called exactly once, with the canonical tail, only when the case expects it. The request is identical afterwards by value, exact type, key order and identity at every level. A rejected resume leaves the log identical too. A successful one keeps exactly the surviving prefix, in place by identity and restored by value, and returns the receipt in contract order.
4. Outcomes are deterministic by value, and rejections do not poison a later resume. Resuming a resumed log discards nothing.
5. Mutation check: each of the 36 one-guard source mutants of store/crash_resume.py fails the corpus, with `ResumeError` and `_fail` rebound to the production class.
   - Boundary mutants: except Exception, ResumeError pass-through for all classes and for each class, and WalError pass-through for all classes and for each class. They are pinned in `FORGE_TARGETS` to their exact forged-case label and must fail exactly that case.
   - Sink handling: isinstance sink output, no token equality, a shared frozen tail, and no restore of the log or of the request.
   - Request and checkpoint checks: isinstance log, request or checkpoint, no request key guard, key length or superset, no negative check or an inclusive one, and no prefix-vs-checkpoint check.
   - Admission: no tail admission, inclusive depth, no alias check, any float, no UTF-8 check, and exclusive digits.
   - Commit and receipt: the commit keeps one entry or is missing, the resume id swaps the counts, and the resumed count comes from the checkpoint.
   - The identity mutant is green. Four equivalent edits are asserted green: `search` for the token grammar and no token grammar (both backed by byte-exact token equality with the same class), no past-log check (always past the prefix too), and an isinstance key check (backed by the exact-type check in `_scalar_ok`).

## Requirement-to-test mapping

- R1, R2, R3: `test_fuzz_cases_hold` (one per generator), `test_corpus_reaches_every_class_and_shape`, `test_every_boundary_error_class_is_forged`.
- R4: `test_determinism_by_value`, `test_no_poisoning_after_rejections`.
- R5: `test_identity_source_mutant_is_green`, `test_mutant_is_red`, `test_equivalent_edits_stay_green`.
