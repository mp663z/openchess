# T0356 Privacy/sensitive flag/contract

This task pins the per-collection sensitive flag that gates cloud-model
egress, following product-report-v5 section 445: "Cloud-model access is
collection-scoped and off for sensitive preparation by default."

- `data/contracts/sensitive_flag.yaml` is the contract, id `privacy-sensitive-flag`.
- `tools/sensitive_flag_contract_lint.py` is the exact structured lint. It
  uses the closed envelope, closed failures and closed errors.
- `tests/test_t0356_sensitive_flag_contract.py` holds the lint and its
  mutation rows, plus a reference engine derived from the YAML with
  happy, boundary, malformed and rollback rows.

## Fail-closed readings where the spec is silent

1. **Default.** The spec does not say which collections count as
   "preparation". An unknown or unset flag reads sensitive, so cloud is off
   by default for every collection. Local is always allowed.
2. **Egress.** Cloud is allowed only when the flag is exactly `false`. The
   verdict is read from current state at send time and is never cached.
3. **Lowering.** Going from true to false needs a user approval token,
   `apv1:` plus sha256 over `collection_id|expected_revision|false`. It is
   bound to one collection and one revision. Its source is the user-approval
   surface only, never model output or imported content.
4. **Raising.** Going from false to true needs no approval and applies
   before the next verdict.
5. **Concurrency.** Compare-and-set on `expected_revision`. A mismatch maps
   to `conflict`.
6. **Rollback (coordinator ruling 22:30: walk-back, not toggle).** Each
   rollback pops ONE history entry and restores it under the same rules
   (restoring false needs a bound approval). A second rollback goes one step
   further back. A rollback is never pushed onto the history, so it can never
   re-apply a value the user just undid. Rollback with an empty history fails
   typed as `empty_history` (code `nothing_to_roll_back`) with state
   unchanged. A set after a rollback continues from the restored value.
7. **Same value.** A same-value set is a no-op and the revision stays
   unchanged.
8. **Revision bound.** The revision is an exact int from 0 through 2**63-1.
   A larger value (for example 10**5000, which cannot even be formatted into
   the approval binding) is malformed_request, never a raw error. The
   inclusive upper edge 2**63-1 is well-formed (on a revision-0 collection it
   fails as stale_revision). Note for the owner batch, not specified here: a
   collection that reaches revision 2**63-1 would be frozen, since 2**63 can
   never be sent back. That is theoretical, and saturation semantics are left
   to a later ruling.
9. **Precedence.** Every malformed_flag_request check runs before
   unknown_collection, stale_revision and the rest. A malformed approval on an
   unknown collection or a stale revision is still malformed_request.
10. **Re-register.** Registering an existing collection is a no-op. It never
    resets state, so an old revision-0 approval cannot be replayed.

## Deferred (flagged, not specified here)

Retry and idempotency-key semantics (T0293) and cancel semantics (T0302)
are out of scope (`role.not_scope`). Redaction, BYOM terms, local model
choice and delete belong to their own contracts (T0392, T0383, T0374, T0401).

## Errors

The failure classes are malformed_flag_request, unknown_collection,
stale_revision, approval_missing, egress_blocked and empty_history. They
map to malformed_request, unknown_collection, conflict, approval_required,
cloud_off and nothing_to_roll_back. `internal` is the only retryable code.

## Hostile rows

The battery covers the three entry points: verdict, transition and
rollback. It uses these request forms:

- a dict subclass, a list and a str as the request;
- str, list and dict subclasses for every value;
- extra keys in 3 forms: plain, `__eq__` raises, and `__hash__` collides;
- a missing key for each field;
- a bytes key;
- int or None for the bool field;
- bool, negative, float or str for the revision;
- grammar edges for the id (63, 64 and 65 hex characters, uppercase,
  trailing newline) and for the destination.

Each row pins `malformed_request`, an empty hostile-call log, the flag
state unchanged and the request unchanged (keys by identity).

## Kill check (executable)

`MUTANTS` in the test file holds 20 one-edit mutants of the reference engine. Each
edit is applied to the file's own source with this kill-check section stripped.
The copy runs in a subprocess from a neutrally named temp dir, with no -k
selection (-k also matches parent dir names, which made v2's harness vacuous).
Green means rc 0 and exactly EXPECTED_BATTERY (140) passed. Red means rc 1 with
at least one failure among 140 run tests. rc 2, 4 or 5 is never a kill. The
identity edit must be green. Each mutant fails a behavioural row, for example
rollback_toggle fails the walk-back rows and apv_match fails the approval
newline rows. They are: apv_match, approval_unbound, bool_as_int, cid_search,
default_open, dest_any, max_rev_lt, dict_sub_ok, no_approval_check, no_cas, noop_bumps,
reregister_resets, rev_bool_ok, rev_unbounded, rollback_empty_default_true,
rollback_no_approval, rollback_toggle, rollback_unknown_first, str_sub_ok and
transition_unknown_first. `EQUIVALENT` holds truthy_egress, asserted green
because stored state is always an exact bool. The lint has a rejecting
mutation for every check, including role, failure classes and triggers, the
failures closure, properties, versioning, links, and record.exact as an exact
bool.
