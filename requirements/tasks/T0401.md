# T0401 Privacy/delete/contract

## Normative requirements

1. `data/contracts/delete.yaml` (`privacy-delete`, `/privacy/delete/v1`) is a closed contract: exact envelope, closed failure model and closed error enum, pinned field by field by `tools/delete_contract_lint.py`. Per collection it owns the user-decided, irreversible local delete, the tombstone and the collection access verdict. It does not own account delete on the control plane (`identity.delete_account`, T0476), account or sync keys, backups, the cloud mode or collection flags (T0365, T0356), BYOM terms (T0383), redaction (T0392), local model (T0374), or retry idempotency (T0293/T0302).
2. Record: `collection_id` (`^col1:[0-9a-f]{64}$`, the T0356 grammar), `state` (exact str `live` or `deleted`), `revision` (exact int 0 to 2^63-1, never bool, derived), `pending` (list of store names not yet erased, in declared store order, empty when live or fully erased). Stores: `content`, `index`, `analysis`, `training`, `ciphertext`, in that order.
3. Register: a new id reads `live`, revision 0, nothing pending. Registering a live id is a no-op. Registering a deleted id is refused `collection_deleted` (tombstone: an id is never reused).
4. Access: a live collection is `allow`. A deleted collection is refused `collection_deleted`, even when nothing is pending. An unregistered id is `unknown_collection`.
5. Delete (live to deleted) needs a decision `^del1:[0-9a-f]{64}$`, which is `del1:` plus the lowercase hex sha256 of the byte-exact preimage: the UTF-8 bytes of `collection_id` verbatim, `|`, `expected_revision` as ASCII decimal (no sign, no leading zeros, zero is `0`), `|`, `delete`, with no leading or trailing separator (example `col1:<64-lowercase-hex>|0|delete`). The decision comes from the user decision surface only. Deletions are never automated. Compare-and-set on `expected_revision`.
6. Order: the tombstone (state `deleted`, every target pending) is written before any store is erased. Then every store is erased in declared order. A store whose erase raises stays in `pending`; later stores are still erased; the collection stays deleted and never reads live again. If an erase raises a BaseException (for example KeyboardInterrupt), it propagates with the tombstone in place and every target pending.
7. Retry: a delete of a deleted collection needs no decision (a well-formed decision is ignored, a malformed one is malformed), keeps the revision, and re-erases only the pending stores. With nothing pending it touches no store.
8. Saturation: a delete is never refused for revision exhaustion. At revision 2^63-1 it writes `deleted` with the revision unchanged. Just below max it commits to max. There is no `revision_exhausted` error.
9. Precedence: malformed request (every grammar and exact-type check, including str/dict/list/int subclasses, non-str keys, a real key replaced by a str subclass, a same-arity renamed key, `__eq__`-raising and hash-colliding extra keys, and a malformed decision) before `unknown_collection`, before `stale_revision`, before the retry, before `decision_missing`.
10. Rollback: a rejected delete or access leaves state, every store and the input unchanged, and calls no store. An accepted delete is irreversible: there is no undelete.
11. Errors: `malformed_request`, `unknown_collection`, `conflict`, `approval_required`, `collection_deleted`, `internal`; only `internal` is retryable. Every raised error is fresh (`__cause__` is None).

## Fail-closed readings

Sources: product report v5 graduated trust ramp table, line 297 ("Never automated | New-line additions, deletions, ... These always require a diff and an explicit decision"), ADR-0004 `data_flow.desktop` (content `store-process`, ciphertext `store`), the control-plane `identity.delete_account` operation (account-level, not owned here), and the coordinator's T0383 ruling that privacy actions are never refused for exhaustion.

- Decision: the spec requires an explicit decision for deletions, so a delete without a bound decision is `decision_missing` (R5).
- Irreversible: the spec is silent on undelete; one would resurrect data the user chose to erase, so none exists (R10).
- Never exhausted: as with the BYOM revoke ruling, a delete is never refused for exhaustion (R8).
- Tombstone: a deleted id is never registered again, so nothing can silently reuse it (R3).
- Partial erase reads deleted: a failed erase never revives the collection (R6).
- Stores: the five store names are invented. ADR-0004 names content and ciphertext; index, analysis and training are the derived local data. A store outside the list is not covered by this contract.

Deferred and flagged, not in this contract: retry idempotency and cancel (T0293/T0302), account delete (T0476 control plane), backups holding the collection, key erasure.
